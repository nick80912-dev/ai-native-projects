## ⚠️ 開始之前:origin 隔離規則(最重要的一條)

**Service Worker、CacheStorage、localStorage 全部是 origin 隔離的。** 在正式站(v18)建立的測試資料,**不會**出現在 GitHub Pages 或任何其他網域上。

因此:

- **B2／B3／C1／C2 的升級流程,必須全程在同一個 Netlify 測試站 URL 上完成**,同一支 iPhone、同一個已安裝的 PWA。
- **GitHub Pages 只能用來驗收 v73 的一般功能(D／E／F／H 區)**,**不得**拿來證明「Netlify v18 的本機資料升級成功」—— 那是不同 origin,證明不了任何事。

### G1 執行順序(**必須嚴格照此順序,不得跳步或換順序**)

順序本身就是驗收內容的一部分 —— 換順序會讓「真實升級路徑」不成立,測到的就不是使用者實際會遇到的情境。

| # | 步驟 | 為什麼順序重要 |
|---|---|---|
| 1 | 同一個 Netlify 測試站部署 **`9eefcb0`**,線上確認是 **v18** | 起點必須是正式站現況,不是任意舊版 |
| 2 | 在 iPhone 安裝**該站**的 PWA,建立測試資料 | PWA 與資料必須綁在這個 origin 上 |
| 3 | **先在 v18 狀態完成離線重開測試(B1),不要先更新** | 錯過就沒有 v18 的離線基準可對照 |
| 4 | 同一個測試站部署 **`5772de5`**;**不得改 origin、不得刪 PWA、不得清網站資料** | 這三件事任何一件都會讓升級路徑從「升級」變成「全新安裝」 |
| 5 | 執行 **B**(SW 更新)與 **C**(升級與混版本驗證) | v18→v73 的一次性窗口只在這裡 |
| 6 | 再驗 **D／E／F／H** 一般功能 | 功能驗收不影響升級路徑,放後面 |
| 7 | **最後**才做 **G**:備份 → 只清單一網域 → 還原 | G2 會清掉資料,提前做會毀掉 B／C 的前提 |

> **⚠️ 全程禁止的操作**(做了就要從步驟 1 重來):
> - 手動 `unregister()` Service Worker
> - 手動清除 CacheStorage
> - 移除後重裝 PWA
> - 中途換到 GitHub Pages 或其他網域繼續驗
>
> 這些都會破壞真實升級路徑。**唯一允許清資料的時機是步驟 7 的 G2,而且只清測試站那一個網域。**

> ### ⚠️ 用 API／CLI 部署時的兩個陷阱(2026-07-31 實際踩到,已解)
>
> **① 部署完成 ≠ 已發布。** `npx @netlify/mcp` 這條路徑會把部署建到 `state: ready`,但 **`published_at` 可能是 `null`** —— 主網域仍服務舊部署。徵狀是「部署顯示成功,但線上檔案沒變」。
> **解法**:到 Netlify 後台該次 deploy 頁面按 **Publish deploy**。驗證方式:比對**部署永久連結**(`https://<deployId>--dev-trippilot-jp.netlify.app`)與**主網域**,兩者不同就是還沒發布。
>
> **② API 部署是差異合併,不是完整快照。** 上傳內容之外、前一版存在的檔案**會留著**。2026-07-31 因此產生過 v18 核心 + v73 殘留檔的混合狀態(`app-version.js` 在 v18 部署下仍回 200,足以讓 C2 前提失效)。
> **解法**:降版部署(新版 → 舊版)必須用**拖放部署**或確認殘留檔已清;升版部署(舊版 → 新版,如 `9eefcb0` → `af520c6`)因為是超集,無此風險。

## C. v18 → v73 資料升級(**同一個 origin,兩個獨立場景**)

> ### 🔴 記團體帳之前務必先讀
>
> **測試站與正式站共用同一個 Google Sheet 與同一個 Apps Script。** 驗收時記的每一筆團體帳都會**永久 append 進正式分帳紀錄表**,依 ADR 0006 append-only,**App 刪不掉,只能由 Bar 直接在 Google Sheet 刪列**。
>
> 更要小心的是:**佇列會在恢復連線時自動送出**。即使當下離線記帳,一旦裝置恢復網路、App 一開機就會 flush 出去 —— 「我等一下再刪掉」是來不及的。
>
> **2026-07-31 桌機彩排時,我自己就踩到了這件事**:以為關掉本機 server 就是離線,但 `navigator.onLine` 仍是 `true`,結果一筆彩排用的假消費被送進正式表(`1784350800000-f4bi`),需要 Bar 手動刪除。
>
> **做法(二選一)**:
> - **建議**:記團體帳之前先到 設定 → 測試模式 打開,這樣紀錄會帶 `[TEST]` 前綴、被正式模式過濾掉、不進統計與結算。驗完記得關掉。
> - 或:C1 只記**個人帳**(純 localStorage,不會外送),團體帳的升級行為改由 `trip_ledger_queue` 是否存活來判斷。
>
> 空白 `分攤成員` 欄的舊格式紀錄會 **fail-open 對所有成員顯示**(`index.html:5800`),所以誤入的列不會只影響自己。

## BB4. Android 實體手機(併入 v112 遺留驗收)

> **這一段原本是 v112 的遺留項目,Bar 於 2026-09-10 裁定併入 v114 一起驗。**
> **2026-09-12 更新**:因 v115 forward bump,本段判準由 v114 改為 **v115**。v115 的正式站已包含 v112、v113、v114、v115 的全部改動,所以在 Android 上驗 v115 等同一次驗完四版。**這不是重做驗收,只是判準版本隨現行 generation 前進** —— BB4 至此仍未執行過。
>
> **最關鍵的是 BB4-a。** v112 修的是一個**只在實體 Android 上才會發生**的缺陷:Chromium 對同源連線數有上限,舊 worker 先並行 fetch 全部資源、卻等 `Promise.all` 之後才由 `cache.put` 讀 response body,未消耗的 stream 會占住連線槽,**讓 Service Worker 永遠卡在 installing**。v112 改為先完整讀成 Blob 再重建 Response。桌機 Chromium 與 Playwright 的 Android 模擬**都重現不出來** —— 只有真手機能證明它真的好了。
