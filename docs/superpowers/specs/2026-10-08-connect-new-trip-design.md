# 個人旅程生命週期：第二階段「連接新旅程」設計

日期：2026-10-08。狀態：**書面規格已確認**：Bar 於 2026-10-08 回覆「照建議」，§9 七項全部採用建議。本文件仍不授權修改程式、Sheet、Apps Script 或正式發布；實作須另行通過 Tier 2 四項確認（Bar 已於 2026-10-08 核准在工作分支實作，不合併、不發布；實作紀錄見 §10）。

程式閱讀基準為正式站 v148（`main` `bdb4925`，與 `dev` 相同）。第一階段設計見 `2026-09-30-personal-trip-lifecycle-design.md`，決策見 ADR 0020。建議在 10/18–10/23 旅程結束、團體帳結清之後，並在 backlog #54（CI 改用 Ubuntu 26.04，期限 11/19）處理之後才動工。

## 1. 目的與範圍

下一趟旅程時，Bar 準備好新的 Google Sheet，每位旅伴在自己的手機上把 App 接到這份 Sheet，不需要等開發者改程式或發布新版。第一階段已經做好「清除並打包旅程」和「過往旅程」，本階段補上最後一段：「目前沒有進行中的旅程」之後，可以接上下一趟。

**範圍內**
- 設定與無旅程首頁提供「連接新旅程」：貼上新 Sheet 的「發布到網路」連結，檢查通過、預覽確認後才切換。
- 新安裝的手機改為顯示「尚未連接旅程」，不再出現內建的岡山行程。
- 所有旅程資料都綁定「目前連接的旅程」：快取、團體帳寫入網址、待同步佇列、備份與封存。
- 提供一份新旅程用的 Sheet 範本，以及 Bar 的開新旅程操作手冊。

**範圍外**（另案）
- 日圓以外的幣別。帳務欄位固定為「日幣／台幣」，去日本以外的國家要另做帳務改版。
- 旅途中直接切換旅程（必須先結束目前的旅程，見 §3）。
- 由一個人替全團切換旅程。依 ADR 0020，每位旅伴各自決定。
- 朋友使用「保存到過往旅程」所需的 Google OAuth 對外發布（見 §9 決策 7）。

## 2. 現況：哪些地方寫死了這一趟

| 寫死的東西 | 位置 | 第二階段的處理 |

另一個相關問題：行程站點的 ID 是「日期＋第幾列」（`MM/DD_i`），打卡、完成／略過、採買綁定都用它。所以在 Sheet 增刪列，這些紀錄會對到別的站。換旅程時本機資料都會清掉，所以不影響切換本身；但新範本可以順便修好這個問題（決策 5）。

## 3. 使用者流程

**狀態**
- **進行中**：目前旅程，行為和現在一樣。
- **已清除**：既有的 `complete` 狀態，首頁顯示「目前沒有進行中的旅程」。
- **未連接**（新）：新安裝的手機，或沒有任何旅程資料的手機。

「連接新旅程」只會出現在「已清除」與「未連接」。進行中的手機要先走第一階段的「清除並打包旅程」，沿用它的安全檢查（沒有待同步、團體帳已結清、沒有待回覆的付款），本階段不另外做一套。

**連接流程**
1. 按「連接新旅程」，貼上 Bar 在 LINE 分享的「發布到網路」連結。可接受 `pubhtml` 或 `pub?output=csv` 格式。如果貼的是一般編輯連結（`/d/…/edit`），提示「請貼『發布到網路』的連結」。
2. 這一步一定要連網：重新下載範本約定的全部分頁，逐一檢查欄位標題，以及 TripConfig 的必填項（旅程名稱、起訖日期、交通方式、匯率、結算幣別、Trip ID、Ledger Endpoint）。
3. 呼叫 Ledger Endpoint 的檢查端點，確認它回報的 Trip ID 與 Sheet 上的相同（§5）。
4. 顯示預覽：旅程名稱、日期、天數、每天站數、目前已加入的成員。使用者按「確認連接」。
5. 一次寫入「目前旅程」紀錄和第一份快取，狀態改為進行中，接著進入選身分。

任何一步失敗都不改變手機狀態，並明確說明失敗原因：網路、連結格式、缺少分頁或欄位、Endpoint 不符，或匯率、幣別無效。

**iPhone 注意**：主畫面 App 與 Safari 的資料是分開的。點開邀請連結只會打開 Safari，無法設定主畫面 App，所以一定要在 App 裡貼上連結。這也是不採用「點連結自動切換」的原因。

## 4. 新旅程 Sheet 範本

- **每趟旅程一份新 Sheet**（決策 1）：從範本「建立副本」。分頁名稱、欄位標題和分頁順序都不能改，分頁也不能刪掉重建。
- **gid 約定**：App 依範本的 gid 抓各分頁。前提是「建立副本」會保留每個分頁的 gid，**這點尚未驗證**，Bar 可以先複製一份現有 Sheet，比對各分頁網址的 `#gid=` 確認。如果不會保留，備案是改從 `pubhtml` 頁面讀出各分頁的 gid，實作前要再評估是否可靠。
- **發布**：檔案 → 共用 → 發布到網路 → 整份文件。不要取消發布，否則連結會失效。
- **Apps Script**：複製時會一起複製。Bar 依手冊部署成網頁應用程式，把產生的 `/exec` 網址填進 TripConfig 的「Ledger Endpoint」。
- **TripConfig 新增項目**：「Trip ID」（範本預填，建立副本後要改成新的一組文字）、「Ledger Endpoint」。
- **可選的新欄位與分頁**（決策 5）：
  - 行程總表新增「行程ID」欄。有填就作為站點 ID，避免增刪列造成錯位；沒填就沿用「日期＋第幾列」。
  - 新增「天氣地區」分頁，欄位為地區名稱、緯度、經度、關鍵字。沒有這個分頁時就不顯示天氣，不再用寫死的城市清單猜。
- 範本中的資料列全部清空，只留標題列。「分帳紀錄」只有 21 欄的標題列。

## 5. 資料與帳務規則

- **目前旅程紀錄**（新 localStorage key）：包含發布 ID、Ledger Endpoint、Trip ID、旅程名稱、起訖日期、連接時間。只在連接成功時寫入；清除旅程時一併刪除。
- **快取綁定**：快取加上來源 ID。開啟 App 時，如果快取的來源和目前旅程不同，就丟棄快取，需要連網重新下載，**絕不顯示 BUILTIN 或上一趟的資料**。離線又沒有快取時，顯示「需要連網下載這趟行程」。
- **團體帳**：寫入、快速拉取和補送都使用目前旅程的 Endpoint。每筆待送紀錄加上 Trip ID，補送前比對，不符的紀錄隔離起來不送，並在資料健康頁顯示。成員身分仍然來自該 Sheet 的「分帳紀錄」，每趟旅程重新選身分。
- **Endpoint 與 Sheet 配對**：`ledger-sync.gs` 新增唯讀的 `doGet?action=info`，回傳它所屬試算表 TripConfig 的 Trip ID，以及分帳紀錄的標題列是否正確。這樣可以防止 CSV 讀 A 表、帳卻寫進 B 表。既有的 `doPost` 和快速拉取的 `after` 參數不變。
- **備份**：新版個人備份加入 Trip ID。還原時 Trip ID 不同就拒絕。沒有 Trip ID 的舊版 v9 備份，只允許還原到「預設舊旅程」（§7）。
- **封存**：`sourceSheetId` 改用發布 ID，並記錄 Trip ID。過往旅程列表可以依旅程分組，不同旅程不會混在一起。

## 6. 失敗語意

- 離線、逾時、CSV 不完整、標題不符、Endpoint 不符或拿不到結果：一律不連接，原狀態不變，可以重試。
- 連接寫到一半中斷（例如寫入失敗或分頁被關閉）：用「準備中」標記，下次開啟時清掉半成品，回到原狀態，不會變成半連接。
- 同一支手機一次只能進行一個生命週期操作，沿用第一階段的互斥鎖。
- 連接後如果 Sheet 被取消發布或刪除：維持目前快取可以離線使用，同步顯示失敗並提示聯絡 Bar；不會自動退回上一趟旅程。

## 7. 舊手機相容（目前的岡山旅程）

把目前寫死的設定包裝成一筆「預設舊旅程」紀錄。尚未清除的手機升級後，視為連接到這筆預設紀錄，行為和現在完全一樣。這些手機清除之後，就走新的連接流程。新安裝的手機一律從「未連接」開始。

**回滾須知**：上線後如果要往前 bump 回滾，新版本必須保留讀取「目前旅程紀錄」的能力，只隱藏連接按鈕。不能把程式退回第二階段之前的版本，否則已連接新旅程的手機會改讀回岡山的 Sheet，把帳寫錯地方。

## 8. 分期、驗收與時程

| 階段 | 內容 | 誰做 | 規模 |
|---|---|---|---|
| 2-0 準備 | 驗證建立副本後 gid 是否保留；整理範本；寫開新旅程手冊 | Bar 操作 Sheet，Claude 寫手冊 | 約 1 小時 |
| 2-1 核心 | 目前旅程紀錄、連接流程與預覽、快取／帳務／備份綁定 Trip ID、`doGet?action=info`、未連接首頁、PWA 改名、ADR 0021、BUILTIN 停用或通用化 | Claude；Tier 2、任務分級 C，動工前送四項確認 | 多次工作階段 |
| 2-2 範本強化（可選） | 行程ID 欄、天氣地區分頁 | Claude；屬資料格式變更，需 Bar 確認 | 1–2 次工作階段 |
| 2-3 演練 | 用一份「測試旅程」Sheet 從頭走一次：連接 → 記帳 → 清除 → 再連接 | Bar 與一位旅伴，實際用手機 | 約 30 分鐘 |

**驗收**
- 單元測試：連結解析、範本檢查、Endpoint 配對、狀態轉換（已清除 → 進行中、未連接 → 進行中）、快取來源不符時丟棄、跨旅程待送紀錄隔離、備份 Trip ID 檢查。
- 瀏覽器測試：用兩份模擬 Sheet 與兩個 Endpoint，確認：
  - 連接 B 後畫面不會出現 A 的任何資料；
  - 離線重開不會出現 BUILTIN；
  - 記帳只送到 B；
  - 任何一步連接失敗時，原狀態都不變；
  - 舊手機升級後行為不變；
  - 沒有 pageerror。
- 真機：iPhone 主畫面 App 與 Android 各走一次 2-3 演練。
- 發布：依 ADR 0019 往前 bump 新版本，走 `dev → main` PR 流程。

**建議時程**：10/24 回國並結清 → 處理 #54（11/19 前）→ 11 月做 2-0 與 2-1 → 2-2 → 下一趟出發前至少兩週完成 2-3 演練。

## 9. Bar 的決定

2026-10-08 Bar 回覆「照建議」，以下七項全部採用建議。第 5 項的「行程ID」欄與「天氣地區」分頁屬資料格式變更，Bar 已一併確認方向；實際欄位定義仍要在實作前的 Tier 2 四項確認中列出。

1. **每趟旅程一份新 Sheet（從範本建立副本）**：建議採用。沿用同一份 Sheet 必須清空分帳紀錄，也無法分辨兩趟旅程的快取與封存。
2. **朋友怎麼接上**：建議各自在 App 內貼上連結。另一個選項是由 Bar 發新版，讓所有手機自動切換，但需要中央設定，而且違反「各自決定」的原則。
3. **只有清除後才能連接**：建議採用，沿用既有的結清與待同步檢查。旅途中直接切換風險高，不做。
4. **新安裝的手機不再顯示岡山行程，改為「尚未連接旅程」**：建議採用，也順便解決「清除網站資料後舊旅程會再出現」的已知限制。
5. **範本要不要加「行程ID」欄與「天氣地區」分頁**：建議加，屬資料格式變更，需要你確認。不加的話，新地區不會有天氣，增刪列的錯位問題也還在。
6. **限定日本（日圓↔台幣）**：確認後，其他國家另案處理。
7. **讓朋友也能用「保存到過往旅程」**：要向 Google 申請 OAuth 對外發布，或把朋友加進測試使用者。可以另案處理，不影響連接功能。

## 10. 實作紀錄（2026-10-08，v149 候選）

依 Bar 核准的 Tier 2 範圍在工作分支完成，PR #51，未合併 dev、未發布。決策記錄於 [ADR 0021](../../../adr/0021-connect-new-trip.md)，操作見[換旅程手冊](../../new-trip-handbook.md)。與本規格文字不同的地方：

- **§5 待送帳的 Trip ID**：規格寫「每筆待送紀錄加上 Trip ID」。實作改為整個佇列一個標記（`trip_ledger_queue_owner`）。換旅程前佇列必須清空，每筆標記沒有額外保護，反而要改 21 欄的帳務格式。不符時整批暫停送出，與規格的「隔離不送」相同。
- **§5 封存的 `sourceSheetId`**：規格寫「改用發布 ID」。實作對新旅程用 `sheet:<Trip ID>`，岡山維持原本的編輯用 ID。原因：Drive `appProperties` 每項上限 124 bytes，發布 ID 加前綴可能超過；Trip ID 也和快照、待送帳、備份一致。封存格式不變（v1），過往旅程列表尚未依旅程分組顯示。
- **§4 天氣地區分頁**：以 TripConfig 的 `Weather Regions GID` 指向分頁（範本尚未建立，無法事先知道 gid）。清單在同步成功後另外下載，存在 `trip_weather_regions`，不進八表快照與封存。
- **§7 舊手機判斷**：「有紀錄」指打卡、下一站進度、想逛、採買清單、個人帳、旅途紀錄、待送帳或三個帳務 bridge 有實際內容；只有快取或成員名稱不算。
- **§8 BUILTIN**：沒有通用化，只限岡山（`legacy`）使用；新旅程沒有快照時顯示「下載行程」。
