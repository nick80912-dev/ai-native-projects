# 新增消費資訊層級調整設計

## 目標

調整單筆新增消費的填寫順序，讓使用者輸入金額與明細後，先處理會改變消費歸屬的代購或分攤成員，再決定是否調整已有預設值的類別、支付方式與日期。

本批只調整 Ledger 新增／編輯表單的顯示順序、收合摘要與鍵盤導引，不修改 Ledger 21 欄、個人／團體儲存位置、Apps Script、Google Sheet、同步或結算語意。

## 現況與問題

單筆表單目前在金額與明細後先顯示 `餐飲 · 現金 · YYYY/MM/DD` 收合摘要，代購 Toggle 或團體分攤成員則在摘要之後。

這會造成兩個問題：

1. 「是否為代購」與「由誰分攤」會改變這筆消費的核心歸屬，資訊優先度卻低於已有預設值的補充欄位。
2. 明細欄目前使用 `enterkeyhint="done"`，按下鍵盤完成會直接儲存；視覺順序調整後若保留此行為，鍵盤使用者仍會跳過代購或分攤成員。

## 核准方案

### 1. 單筆個人帳順序

保留表單頂端既有的身分、多品項切換、帳本與幣別控制。其後順序調整為：

1. 金額。
2. 明細。
3. 代購 Toggle。
4. Toggle 開啟時原地展開「幫誰買」。
5. 「其他資訊（可選調整）」摘要與內容。
6. 稅與優惠券。
7. 更多細節。
8. 儲存與「儲存並再記一筆」。

代購區維持獨立資訊層，不包進其他資訊的淡色容器。Toggle 與明細間距為 8–10px；代購區與下一區間距為 12–14px。

### 2. 單筆團體帳順序

團體帳沒有代購 Toggle，改將「分攤成員」放在明細後、其他資訊之前：

1. 金額。
2. 明細。
3. 分攤成員。
4. 「其他資訊（可選調整）」摘要與內容。
5. 稅與優惠券。
6. 更多細節。
7. 儲存與「儲存並再記一筆」。

分攤成員仍使用既有正式成員選擇與驗證，不新增另一套名單或預設規則。

### 3. 其他資訊摘要

收合狀態必須同時顯示區塊名稱與目前值，不能只顯示「其他資訊」：

```text
其他資訊（可選調整）
餐飲｜現金｜今天　⌄
```

摘要資料依序為：

1. 類別。
2. 支付方式。
3. 日期。

日期顯示規則：

- 與 `appNow()` 的裝置本地日期相同：`今天`。
- 同年度的其他日期：`M/D`，例如 `10/18`。
- 不同年度：`YYYY/M/D`，例如 `2027/1/3`。

比較日期必須沿用 App 既有可模擬時鐘，不直接另讀 `new Date()`，避免旅行日測試與畫面摘要不一致。

使用全形分隔線 `｜`，不使用膠囊逐欄包裝。摘要值必須在收合與展開狀態都可見，讓使用者第一眼判斷是否需要調整。

### 4. 其他資訊展開內容

展開後沿用既有欄位與資料來源：

- 店家。
- 日期與時間。
- 類別。
- 支付方式。

區塊使用現有海洋主色的極淡底色或灰藍底色、1px 淡邊框、10–12px 圓角及 10–12px 內距。不得使用 coral；coral 保留給提醒、錯誤或主要高權重操作。

「可選調整」的意思是系統已有預設值，使用者可以不展開修改；不代表類別、支付方式或日期不會寫入紀錄。

### 5. 鍵盤與焦點流程

- 單筆明細欄的 `enterkeyhint` 由 `done` 改為 `next`。
- 按下下一步不得直接儲存。
- 個人帳將視線與捲動位置導向代購 Toggle；不自動開啟代購。
- 團體帳導向分攤成員區的第一個可操作控制。
- 使用者仍可隨時直接點底部儲存，既有驗證規則不變。
- 驗證失敗若位於收合的其他資訊內，系統必須先展開區塊，再定位或提示錯誤欄位。

## 多品項邊界

多品項不套用單一總代購 Toggle：

- 個人帳維持每個品項各自設定代購與對象。
- 團體帳的共同分攤成員維持在品項清單之前。
- 多品項帳單資訊摘要、店家必填、逐項分類與稅務流程維持現況。

本批不得把單筆表單的「其他資訊」元件直接套到多品項，造成兩套不同責任的帳單資訊混合。

## 元件邊界

預計調整以下顯示層責任：

- 單筆主要欄位 renderer：只輸出金額與明細。
- 單筆帳本歸屬 renderer：依 track 輸出個人代購或團體分攤成員。
- 其他資訊摘要 helper：由 draft 與 `appNow()` 產生 `類別｜支付方式｜日期`。
- 其他資訊 disclosure：負責摘要、展開狀態與既有次要欄位。
- 明細鍵盤 handler：只負責移往下一個決策區，不負責儲存。

不得複製類別、支付方式、日期或成員的驗證與資料來源。

## 錯誤與退化

- 無法解析日期時，摘要不得偽裝成「今天」；顯示 draft 原值並由既有日期驗證處理。
- 類別或支付方式因設定變更而暫時無效時，摘要仍顯示 draft 原值，儲存時由既有 validator 阻擋。
- 個人帳未開啟代購時，不渲染對象選擇。
- 代購開啟但未選對象時，維持既有必填錯誤。
- 團體帳至少一位正式成員的規則維持不變。
- 切換個人／團體帳時仍由既有 draft 切軌契約處理；C 批的逐項資料保留問題不在本批偷偷修正。

## 測試

### 自動測試

- 單筆個人帳 DOM 順序為明細 → 代購 → 其他資訊。
- 單筆團體帳 DOM 順序為明細 → 分攤成員 → 其他資訊。
- 其他資訊收合時仍輸出類別、支付方式與日期摘要。
- 當天顯示 `今天`，同年度與跨年度日期依契約顯示。
- 摘要使用 `｜` 且不得把三個值拆成獨立膠囊。
- 展開後仍包含店家、日期／時間、類別與支付方式。
- 明細 Enter 不再呼叫儲存，並依 track 導向正確區域。
- 收合區內驗證失敗時會先展開。
- 多品項仍維持逐項代購，沒有新增單一總 Toggle。

### Browser QA

以 320×700、375×812、390×844 驗證：

- 個人／團體單筆的完整順序。
- 代購開關前後的原地展開與捲動位置。
- 分攤成員一位、多人及長姓名。
- `餐飲｜現金｜今天` 收合摘要第一眼可辨識。
- 非今天與跨年度日期摘要。
- 其他資訊展開後無水平溢出。
- 軟體鍵盤下一步不會誤儲存。
- 所有可操作控制至少 40px，主要儲存按鈕至少 44px。
- console error／warning 為 0。
